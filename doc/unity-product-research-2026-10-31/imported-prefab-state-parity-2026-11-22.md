The more defensible distinct purpose is **comparing selected actual loaded prefab values across two installed Unity Editors, using the exact same original `.prefab` and `.meta` bytes**. The previously built **Publisher Version Matrix** already proved equality of the source files and importer metadata but did not measure values after native Unity loading. This new product is separate: **HPR Imported Prefab State Parity** uses `PrefabUtility.LoadPrefabContents` in isolated scenes and `UnloadPrefabContents` without saving; it snapshots hierarchy, component inventory and selected fields relevant to 3D/animated prefab compatibility. The official API documentation states LoadPrefabContents loads a prefab into an isolated scene and UnloadPrefabContents releases it without altering the asset. Sources:

## Scope and non-claims

This is **not a general serialization difference engine** and not a claim to support Unity 7 before an actual Unity 7 installation exists. The first original tool captures hierarchy paths, active/tag/layer/static flags, local Transform position/rotation/scale, Renderer material references, Animator controller/avatar references, covered Collider values and Rigidbody settings. All remaining component types are counted explicitly as **unsupported**, and their values are **not** silently treated as verified. Unity's `EditorJsonUtility.ToJson` and `SerializedObject` can access broader fields, but raw object serialization can contain noise or scene-local references; the first product intentionally limits which values it can compare stably across Editors. The exact two-editor comparison returns one of three separate conclusions: changed original inputs (not attributable to Unity), different covered native imported values (review required), or covered values matching (only the declared subset, not full parity). No source file, prefab, project setting or business account is modified.

The tool is built entirely on public first-party Editor APIs, with no network calls or runtime assembly, requires two disposable Unity projects and only actual source assets that the publisher owns. Source content is private with a candidate-only license status. The native QA must use fresh author/export and independent buyer import in both Unity 2022.3.22f1 and 6000.6.8f1, three original first-party animated prefab teaching examples, original `.unitypackage` identity verification, separate synthetic negative controls, exact matched-source checks, readable original GUI screenshots and official Asset Store Tools validation. One passing source test or one Editor success is never a buyer-ready proof.

## 23 November native read-only dependency-provenance correctness correction

### Source evidence and precise buyer harm

The earlier tested `uxfinal59d` release fingerprints the original `.prefab` and its adjacent `.meta` file, then compares a selected set of **actually loaded Unity prefab fields**. However, a byte-identical prefab can refer to a material, FBX mesh, runtime controller, script, or nested prefab whose **source bytes or importer settings are different** in the other Unity installation. A formerly clean loaded-value match could be misleading; a detected difference could be wrongly attributed to Unity rather than the referenced input. For a publisher deciding whether to upgrade multiple client projects, this is a correctness gate, not a cosmetic addition.

Unity's official `AssetDatabase.GetDependencies` documentation describes `recursive=true` as including directly and indirectly referenced asset paths. Its Asset Database refresh guidance explains static and dynamic dependencies, including importer versions and build target, can trigger reimports. Crucially the Unity 6.4 upgrade guide notes that asset import artifact dependency changes now trigger reimport only when the imported artifact changes, and some custom importers may need explicit source dependencies. These are official technical facts, *not* customer survey or paying demand evidence. The API does **not** prove it covers all custom importer/environmental dependencies.

Sources: https://docs.unity.com/en-us/engine/6000.3/script-reference/unityeditor/assetdatabase/getdependencies ; https://docs.unity.com/en-us/engine/6000.0/manual/assets-and-media/asset-database/refreshing ; https://docs.unity.com/en-us/engine/6000.6/manual/upgrade-guides/upgrade-guide-unity64 .

### Revised strict product behavior and withheld claims

The scanner's new **schema-two native JSON snapshot** includes recursively referenced physical `Assets/...` input files, stable Unity GUID, original file SHA-256, and adjacent importer `.meta` SHA-256 in bounded read-only input. It explicitly records any nonphysical built-in or package-provided dependency paths for which source-byte identity was **not verifiable** rather than pretending every dependency is covered. A missing/oversized/unstable readable asset, too many references or canceled scan fails closed. Earlier schema-one receipts, which do not provide this evidence, are rejected and must be recaptured in each real Editor.

Priority of conclusions: changed original prefab source blocks Unity attribution; changed referenced source or importer metadata blocks Unity attribution; unresolved built-in/package dependencies block an unqualified clean verdict; otherwise covered imported values are compared and reviewed. This remains **a subset-of-fields comparison**, not a serialized-object, Player-build, custom MonoBehaviour, importer environment, or Unity 7 certification. This deliberately reduces false positives and makes its unknowns clear, but may reduce the number of clean results for projects with package-cache or built-in assets. Avoid claiming broad buyer compatibility until actual original native QA on real imported prefabs and genuine difficult variants is observed.

Developer-level implementation and all test receipts stay in the source repository and the Raspi project exchange; no user-facing report should narrate every technical check or imply real marketplace publication. ### Additional independent evidence — missing dependencies remain invisible to ordinary asset-reference scans

Unity's own issue UUM-130890, closed as designed for Unity six point three through six point five, reports ScriptedImporter serialized references unexpectedly null after a reimport. Unity's resolution states the importer did not **declare a needed prefab artifact dependency**, and explicitly directs the developer to register it with `AssetImportContext.DependsOnArtifact`. That is a documented failure mode caused by **undeclared** dependency behavior, not by physical source bytes changing. Unity's 6.4 artifact-dependency discussion includes a concrete nested-model example and a developer reporting missing material dependencies across machines. A January 2026 Unity technical discussion identifies the built-in Import Activity window as a way to diagnose import reasons and referenced assets.

Sources: https://issuetracker.unity.com/issues/18577/scripted-importer-serialized-members-are-null-when-reimporting-all-assets ; https://discussions.unity.com/t/narrowing-artifact-dependencies-in-unity-6-4/1690877 ; https://discussions.unity.com/t/reducing-assets-import-times-in-unity/1702346 .

**Critical limitation:** `AssetDatabase.GetDependencies(..., true)` only reports what Unity's Asset Database knows as referenced assets. It cannot guarantee discovery of an importer dependency that custom code failed to register, nor does source SHA-256 capture an imported artifact hash, the platform/build-target, project settings, or the actual import activity chain. The new product therefore says **verified referenced physical `Assets/...` dependency inputs**, not “all Unity dependencies guaranteed identical.” If publisher demand justifies it, a separately tested complement could compare Unity's Import Activity diagnostics and imported outputs, but that is **not implemented or buyer verified here**. No evidence of a paying buyer was established by these issue discussions.

## Scope and non-claims

This is **not a general serialization difference engine** and not a claim to support Unity 7 before an actual Unity 7 installation exists. The first original tool captures hierarchy paths, active/tag/layer/static flags, local Transform position/rotation/scale, Renderer material references, Animator controller/avatar references, covered Collider values and Rigidbody settings. All remaining component types are counted explicitly as **unsupported**, and their values are **not** silently treated as verified. Unity's `EditorJsonUtility.ToJson` and `SerializedObject` can access broader fields, but raw object serialization can contain noise or scene-local references; the first product intentionally limits which values it can compare stably across Editors. The exact two-editor comparison returns one of three separate conclusions: changed original inputs (not attributable to Unity), different covered native imported values (review required), or covered values matching (only the declared subset, not full parity). No source file, prefab, project setting or business account is modified.

The tool is built entirely on public first-party Editor APIs, with no network calls or runtime assembly, requires two disposable Unity projects and only actual source assets that the publisher owns. Source content is private with a candidate-only license status. The native QA must use fresh author/export and independent buyer import in both Unity 2022.3.22f1 and 6000.6.8f1, three original first-party animated prefab teaching examples, original `.unitypackage` identity verification, separate synthetic negative controls, exact matched-source checks, readable original GUI screenshots and official Asset Store Tools validation. One passing source test or one Editor success is never a buyer-ready proof.

## 23 November native read-only dependency-provenance correctness correction

### Source evidence and precise buyer harm

The earlier tested `uxfinal59d` release fingerprints the original `.prefab` and its adjacent `.meta` file, then compares a selected set of **actually loaded Unity prefab fields**. However, a byte-identical prefab can refer to a material, FBX mesh, runtime controller, script, or nested prefab whose **source bytes or importer settings are different** in the other Unity installation. A formerly clean loaded-value match could be misleading; a detected difference could be wrongly attributed to Unity rather than the referenced input. For a publisher deciding whether to upgrade multiple client projects, this is a correctness gate, not a cosmetic addition.

Unity's official `AssetDatabase.GetDependencies` documentation describes `recursive=true` as including directly and indirectly referenced asset paths. Its Asset Database refresh guidance explains static and dynamic dependencies, including importer versions and build target, can trigger reimports. Crucially the Unity 6.4 upgrade guide notes that asset import artifact dependency changes now trigger reimport only when the imported artifact changes, and some custom importers may need explicit source dependencies. These are official technical facts, *not* customer survey or paying demand evidence. The API does **not** prove it covers all custom importer/environmental dependencies.

Sources: https://docs.unity.com/en-us/engine/6000.3/script-reference/unityeditor/assetdatabase/getdependencies ; https://docs.unity.com/en-us/engine/6000.0/manual/assets-and-media/asset-database/refreshing ; https://docs.unity.com/en-us/engine/6000.6/manual/upgrade-guides/upgrade-guide-unity64 .

# Player-only ScriptableObject reference checks — November 23, 2026

## Scope, narrow observed public pain, and commercial decision

A specific October 9, 2026 Unity developer reports that ScriptableObject fields pointing at game item prefabs work in the Editor but become null in a built game, while other data remains. The developer says both ScriptableObject and prefab are under `Resources` and the failure happens after trying to instantiate the referenced object. Thread participants asked whether the ScriptableObject was written dirty / serialized correctly and how source items were loaded, so **the cause is not independently established and must not be reported as a confirmed Unity engine defect**. This is one real user report, not validated purchasing demand. Source: https://discussions.unity.com/t/prefabs-stored-within-scriptable-objects-losing-reference-only-in-build/1738784 .

## Separate first-party candidate and functional boundaries

New separate first-party source is `unity/tools/release/player_reference_probe/Assets/HPRPlayerReferenceProbe`, with `Runtime/HprPlayerReferenceProbe.cs` and `Editor/HprPlayerReferenceProbeWindow.cs`. The opt-in scene component takes one to sixty-four explicitly named ScriptableObject fields, including direct `UnityEngine.Object` references that Unity serializes as public instance fields or `[SerializeField]` private fields, and inspects them by exact field name at game launch. It logs a structured runtime JSON receipt and can write a new local JSON to `Application.persistentDataPath` using create-only access. The Editor window scans a deliberately selected scene probe without modifying project files and can create a new Editor baseline, load an existing Player report, and compare them in C#. It reports `PLAYER_REFERENCE_LOSS_REPRODUCED` only if an explicitly selected field is assigned in an Editor baseline but null in a **same-Unity-version actual Player receipt**. An intentionally null field in both is `CONSISTENT_NULL_OR_UNSET_FIELDS`, not an engine bug. Any missing/invalid field type or malformed report is marked incomplete; no unknown or nested field is silently considered checked.

This **does not claim to scan every ScriptableObject**, class, private field, list, `[SerializeReference]` tree, dynamic Addressables operation, platform build behavior, unloading, scene ownership or arbitrary Player incompatibility. The Player component can create extra runtime logs only after a developer explicitly adds it to a scene, and docs instruct removing/disabling it after debugging. No connection, telemetry, online service, asset mutation, automatic build or automatic account submission. Private native author, fixture and test runners are kept outside the consumer subtree and never enter the original `.unitypackage`.

**Important technical discovery affecting the product design:** placing a `ScriptableObject source` reference directly on the scene-based test component can cause Unity to include that asset in the Player and thus mask a missing-source failure that otherwise existed. Unity's official Resources documentation confirms path-based `Resources.Load<T>(extensionlessPath)` and Resources folders' inclusion behavior. New source therefore offers an explicit **path-only, non-pinning** mode for ScriptableObjects under Resources; it refuses simultaneous direct source and Resources path. The newly shipped buyer README explains the distinction, avoiding a misleading product claim. The inspector records lookup mode in schema-two receipts and can report `PLAYER_SCRIPTABLEOBJECT_SOURCE_NOT_LOADED` separately from a null referenced field. This does not solve stripped assets, Addressables, scene ownership or non-Resources loading; these remain outside the product. This revision needs its own genuine actual Player native QA and official validation before publication.

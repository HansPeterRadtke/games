# HPR Unity Suite — code, configuration and Editor experience audit (pre-implementation)

Snapshot: 31 October 2026, integration worktree `product/unity-integrated-suite-20261030`. This is a **source-based pre-development risk register**, not a bug-fix changelog. All suspected defects require targeted failing tests followed by fixes, unless already supported by observed Editor logs. Source references are to the mutable worktree and line numbers as observed today; recheck after revisions. User-directed priority: research and technical scrutiny before expanding implementation.

## Product quality conclusion

The suite is a compact teaching framework, **not** an advanced production-ready toolkit. Original ten runtime module sources: 47 C# scripts, ~2,294 physical source lines including comments/whitespace. Integrated sample controller alone is ~33 KB and editor builder ~26 KB; the shipping demo is a geometric scene using IMGUI and simple controls. The latest prior test receipts show successful original Unity 6.4 and 6.6 cleanroom import and ten gameplay integration checks; the Unity 6.6 import emits a deprecated C# API warning. Tests do not establish accessibility, satisfactory installation time, all render/input backends, robustness in an existing project, or third-party integration. The branch also contains other unpublished development work: **do not stage or overwrite it while researching**.

## Confirmed functional/product issues

**Critical — Not sufficiently configurable:** `Integration/HprGameplaySuitePlayground.cs` has serialized references to a handful of game assets, but effective gameplay policy is hardcoded: `InteractRange = 2.7f` and `MoveSpeed = 4f` at ~53–54; fixed healing magnitude and stamina/weapon settings across methods; fixed key bindings and arena boundaries. `Editor/HprGameplaySuiteSceneBuilder.cs` similarly resets item IDs, stats, ability costs/cooldowns, materials and demo geometry to built-in numeric values. The owner’s `configuration.md` requires parameter taxonomy, units, accepted ranges, documented defaults, incompatibilities and one source of truth. Do not turn every invariant into a slider; use a coherent versioned `ScriptableObject` game/demo configuration with validated Inspector fields, overridable through the public API for professional users. The *core* should remain independently configurable without the demo.

**Critical — Unannounced destructive Editor demo rebuilding:** `HprGameplaySuiteSceneBuilder.BuildShowcase` obtains existing ScriptableObject assets through `CreateAsset`, then overwrites their fields and `EditorUtility.SetDirty`; it also calls `EditorSceneManager.NewScene` and saves to the same demo-scene path. Editing existing sample settings and choosing Build Showcase can therefore overwrite buyer customizations. Proposed gate: preview/dry-run, refuse overwrite by default; explicit confirm to replace with a backup; use public `Undo` for Editor modifications and safe add-only sample generation; never write outside the package sample root; preserve and test preexisting unsaved scene and package assets across cancellation/failure. This is **source-confirmed risk**, not yet tested data loss in buyer UI.

**Critical — Official Unity 6.6 deprecation warning observed in actual imported buyer archive:** `HprGameplaySuiteSceneBuilder.cs` ~463 calls `AssetDatabase.ExportPackage(string,string,ExportPackageOptions)`, which Unity 6.6.7f1 emits as `CS0618` obsolete. Unity 6.6 submission guidelines explicitly reject deprecated/obsolete API warnings. Need a public-API-compatible exporter for current Editor and a legacy-only compilation path *if still supporting older versions*. Tests: 6.4 and 6.6 cleanroom compile, zero code warnings, exact output asset graph.

**Critical — Input backend incompatibility risk:** `HprGameplaySuitePlayground.Update` uses `Input.GetKey`/`GetKeyDown` and `Input.mousePosition` exclusively; modern Unity projects often select Input System-only active handling. The demo may continuously throw and fail to accept input in that configuration. Needs a bridge isolated behind an input interface and tested with old, new and both active handling, without forcing an unnecessary package dependency. This is a source-based compatibility risk, not yet a reproducibly measured failure in the current tests.

**Critical — Current editor experience does not match best-of-class:** HPR lacks a guided authoring workflow with searchable, validated settings and visual feedback. Runtime `OnGUI` ~594 starts at fixed `Rect(12,12,550,480)`, no responsive viewport, keyboard navigation, scaling or documented font limits. All controls are minimal script buttons. Owner GUI guidelines require first-screen question, immediate action acknowledgement, loading/invalid/empty/error/disabled states, visible recoverable validation, and multiple window-size/scale tests. Unity’s 2025 UI Toolkit book provides a concrete separate UXML/USS/binding design. Proposed purpose-first flow: Open Demo / Configure Systems / Test Integration / Export Evidence. Advanced data lives in the Inspector with explicit tooltips, range and error messages. **Do not** replace the whole Unity Editor or install GUI dependencies without buyer need.

**High — HPR EventBus unsubscribe by delegate identity:** `EventBus.Subscribe<T>` appends a subscription entry; `EventBus.Remove` ~97 calls `handlers.RemoveAll(entry => entry.Handler == handler)`. Subscribing the same callback twice and disposing one subscription appears to remove both, violating independent subscription-token semantics. Design a failing test before fix; if duplicate callbacks are deliberately deduplicated, document it and make Subscribe reject duplicates rather than silently alter behavior.

**High — ServiceRegistry re-registration stale lifecycle:** `ServiceRegistry.Register` ~36 overwrites the `services[serviceType]` mapping but retains old service in `serviceOrder` when a replacement instance is provided. `ResolveAll`, tick order, initialization and disposal may then process stale services; `TryResolve<T>` falls back to the first compatible `serviceOrder` type. Required contracts: explicit replace/remove semantics, idempotent init/disposal, ownership of disposed services, deterministic resolution priority, error for ambiguous registrations. Tests must cover repeated registration, replacement during running session and shutdown.

**High — Inventory overflow and invalid snapshot states:** `InventoryComponent.AddItem` computes delta by multiplying `amount * Mathf.Max(1,data.Value)` then adds to the existing `int`, without explicit checked overflow or max capacity; `RestoreItemQuantities` ~139 unconditionally clears inventory and admits arbitrary positive IDs/quantities (unknown items not validated in module). The demo host validates two particular item IDs, but this is not a general-purpose Inventory SDK validation. Need semantic item-key uniqueness, quantity/max bounds, unknown-item and duplicate behavior, checked arithmetic, transactional reject-before-mutation and independent replay tests.

**High — Save storage is only an example, not a complete SDK:** `HprSuiteSnapshotStorage` version three wraps one local JSON file. File.Replace support differs by platform; no recovery backup, encryption, schema migrations, large-world streaming, cloud or multiplayer consistency. `HprGameplaySuitePlayground.RestoreSnapshot` constructs validated combat state first, but then mutates transforms/stats/inventory before applying ability restore. Ability snapshot validation does not establish complete transactional rollback for every nested state. Test invalid nested ability data, duplicate IDs, exception injection after some stages, crash between temporary writes, unsupported file replace and older schema. Do not market the present Save module as Easy Save-equivalent.

**High — Weak enemy/weapon feature depth:** `EnemyRuntimeState.Decide` is only a distance, attack-cooldown and AI-type selector; its integrated adapter moves directly toward the player, not along a computed navmesh. `WeaponRuntimeState` covers magazine, damage, range, fire delay/reload, but player demo is a single raycast and one stationary/chasing enemy. Mature competitor tools provide designers with complex graphs/behaviors, multiple collision/raycast modes, VFX, animation, damage categories, controller input, equipment and save integration. Avoid unsupported marketing terms. If expanding these modules, target a distinct user task instead of matching existing tools feature by feature.

**High — Cross-module coupling and asmdef migration surface:** all original scripts use broad `HPR` root namespace despite ten `HPR.*.Runtime` asmdefs; consumers may already have a collision from rejected standalone module packages. Adding package to a large existing project should provide explicit migration/conflict errors, a conflict-free prefix (with serialized script/GUID migration plan), and separate Editor, runtime, samples and optional tests. Never rename assemblies/GUIDs ad hoc: serialized scene references and existing package users must survive upgrade.

**High — Imported package and release build differ from mutable source:** current dirty worktree has modifications made after the last built and cleanroom-verified buyer archive; source tests and old receipts are not proof of final package QA. Rebuild and independently test the exact candidate after every source change; retain hashes/source inventory/Unity versions and downloaded dependency manifest for each tested release. Use ordinary Unity Test Framework properly and add a CI runner with error/warning policy. Original 2026 October Unity Store AI rejection still stands; no provider submission approval.

**Medium — Hot-path allocation / event dispatch:** `EventBus.Publish` enumerates all subscription event types and allocates a new collected list/snapshot per call; `FindNearbyInteractable` creates a short array and component query; HUD performs strings and per-frame GUI calls; `FireAt` allocates `RaycastHit[]` via `Physics.RaycastAll`. These are not automatically unacceptable for small demos. Profile first, then choose bounded, nonalloc variants if representative device/frame/alloc measurements show a problem. Do not add concurrency or caching without measurements.

**Medium — Test-contract readability:** manual assertions in the imported-package smoke tool are programmatically useful but opaque to normal buyers. Official Unity Test Framework supports EditMode and PlayMode with asmdefs, NUnit test names and reports. Provide a small optional, public sample test suite that buyers can run without shipping NUnit into runtime; retain heavy private CI cleanroom tests in the development repository. Test names should state behavior and failure message explain expected versus actual, not generic 'QA assertion failed'.

**Medium — Extension and isolation:** The demo monolith ties actual game actor instances to Unity-specific `MonoBehaviour`, physics and its own `InventoryComponent`. To differentiate as a *source-level integration* product, consumers must be able to adapt existing player/item/save systems via narrow interfaces without replacing their project, and unplug the package without destroying assets. A generic `CompositionRoot` alone is not proof of that user story. Provide explicit adapter hooks and a real third-party or intentionally incompatible fixture in tests only after validating customer demand.

## Per-setting configuration contract (candidate schema, not implementation)

Each proposed option needs name, owner, type/unit/range, default, variation reason, impact and validation; sample groups:

- Player control: move speed meters/second (range >0), input implementation old/new/custom adapter (explicit dependency and availability gates), camera selection behavior, collision layers. Do not expose a misleading tuning value that is never used.
- Interaction: detection mode proximity/camera raycast, maximum reach meters, obstruction mask, priority/distance tie-breaker, input action binding, callback failure reporting.
- Weapon: damage points, range meters, fire interval seconds, magazine and reserve capacity count, reload duration seconds, hit mask, damage interface/friendly fire, physics sync and multi-hit policy.
- Enemy: decision policy ScriptableObject or code strategy, detection/chase/attack distances meters, movement speed meters/sec, attack cooldown seconds, LOS and obstacle/navigation mode; 'not implemented' modes must be visually disabled rather than silently accepted.
- Abilities: action mappings, cost stamina units, cooldown seconds, area radius meters, effects registry, target/self filtering, effect stacking, valid state transitions.
- Save: schema/revision, path/slot policy, sync/async mode, backup and atomic replacement support by platform, migration choices, validation, max serialized size. Never expose arbitrary unsanitized public file paths to nontechnical users.
- Editor: auto-preview only, non-destructive defaults, no side effects on import/assembly reload, beginner/advanced visibility, rollback and preview dry-run, actionable validation output, persisted user preferences only with explicit consent.

## Required acceptance suite before 'best code' claim

An external professional Unity developer should be able to import into an **already populated** Unity project with pre-existing components and custom editor settings, open a demo and produce a meaningful visible result without losing or modifying unrelated files. Establish measurable baseline and test across fresh and dirty projects, supported Unity versions including 6.6, Built-in and URP at minimum, old/new input handling, domain reload on/off twice, Windows/macOS/Linux Editor availability where claimed, small Game View/Inspector sizes and font scales, retry/undo/cancel paths, corruption and forced I/O failure, upgrade from prior supported version, duplicate assemblies, event handler lifecycle, saved-state boundaries and ownership. Human play-test and UX observer are essential; code execution tests alone cannot certify commercial usability.

Success must include zero obsolete/unexplained warnings, zero unrelated asset mutations, no purchase/install/download on import, explicit opt-in for potentially destructive operations, clean assembly/domain unload, and a traceable receipt for every actual test environment. The GUI must show which task is possible, what it does, progress and failure corrective actions. If a critical gate fails, the release remains internal.

## Test-first development order after research is accepted

First write contract tests for EventBus subscription identity, ServiceRegistry replace/disposal, inventory overflow and cross-module snapshot atomicity; use real Unity EditMode. Then define semantic configuration and Unity Inspector validation, with custom style guide and refactoring. Then make demo builder non-destructive and input-adapter compatible. Then implement first-time user experience using UI Toolkit only where justified, not hardwire an entire new UI stack into runtime modules. Finally verify actual imported archive in fresh/dirty project, official Asset Store Validator, newer Editor disabled domain reload, both input backends and visual/UX review. Do not extend generic enemies/weapon features until market research identifies a distinctive customer task.

## Actual vs unverified

Observed: source structures, hardcoded values, API patterns, module sizes, buyer archive Unity 6.6 obsolete API warning, old Unity imports/tests and screenshots. Hypothesized until tests: duplicate handler unsubscribed incorrectly, service replacement lifecycle, concrete player-input failure with new Input System-only, partial save rollback in pathological cases, consumer overwrites from Build Showcase. The audit deliberately does **not** claim these untested cases already failed in a running customer project.

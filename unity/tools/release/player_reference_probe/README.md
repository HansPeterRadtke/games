# HPR Player Reference Probe — original private Unity product candidate

This is a separate, opt-in Unity Editor and runtime diagnostic intended for developers who suspect a direct ScriptableObject prefab reference works in the Editor but is missing or different in the built Player. It is a new development candidate, **not** an approved or published Unity Asset Store product. It does not replace the existing prefab-state comparison tool or the broader shared seller; no account operation, external upload, telemetry, analytics, or customer contact is implemented.

## Buyer workflow

Import the original `Assets/HPRPlayerReferenceProbe` subtree into an isolated copy of your actual Unity project. Create an empty GameObject in a specific test scene and add `HprPlayerReferenceProbe`; in the Inspector enter up to sixty-four uniquely named checks, choose the ScriptableObject to inspect, and enter exactly one serialized direct `UnityEngine.Object` field name such as `itemPrefab`. This tool only reads the exact fields deliberately selected. In Unity, open **Tools → HPR → Player Reference Probe**, select the probe object and choose **Inspect selected scene probe — read only**. Optionally save a new Editor baseline JSON with a create-only file dialog; the original file is never overwritten.

Build and run the game using your own build settings. The runtime scene probe checks the specified fields when that scene starts in the actual Player, logs the structured `HPR_PLAYER_REFERENCE_RECEIPT=` JSON marker, and can create one new private JSON report in the local `Application.persistentDataPath` folder (the filename contains a random suffix, not overwritten). The console logs the local filename. Return to the Editor and use the window's file selectors to compare the original Editor baseline against an actual Player-generated JSON report from **the identical Unity version**. This is not an automatic build, a scene injector or a synthetic simulation. Remove or disable the test component when you do not need runtime logging.

The tool can report `PLAYER_REFERENCE_LOSS_REPRODUCED` when an explicitly selected reference is assigned in the Editor but null in the built Player. It can also report consistently null or intentionally unset fields, changed target identity, unsupported fields, and a narrow match for successfully checked fields. A null field is **not** proof of a Unity bug, because leaving references empty can be intentional. No automated repair or assignment is performed.

## Technical and commercial boundaries

Only direct `UnityEngine.Object` fields which Unity normally serializes are eligible: public non-static fields and private fields annotated `[SerializeField]`. Collections, `[SerializeReference]` graphs, nested classes, private nonserialized fields, renamed properties, Addressables lifetimes, Player stripping, script compilation, static/dynamic loads and runtime scene destruction are not inspected. A result explicitly describes its narrow scope; it is not full build certification. The runtime component changes Player behavior only when the buyer explicitly adds it to a scene. The Editor UI does not modify source assets, prefabs, scene files or project settings in its inspection/compare path. There is no network access, no external DLL and no third-party source. Original tests create their own disposable Unity projects; the private first-party sample scene and build QA code are **not included** in the buyer archive.

A reported build-only prefab-reference failure exists in the October 2026 Unity developer discussion at https://discussions.unity.com/t/prefabs-stored-within-scriptable-objects-losing-reference-only-in-build/1738784 . The general Unity missing-reference validator segment is already crowded (e.g., RefSafe Pro, Release Check Pro and Missing Reference & None Field Finder). This addresses a narrower need, but an actual paying buyer, price advantage, adoption, future support cost and platform listing approval are **not verified**. The ONE shared seller owns any legal disclosure, pricing, bundle decision and separately authorized external listing.

## Actual Player path-only diagnostic improvement, November twenty-three

The original Unity6 direct scene fixture demonstrated real Player inspection, two surviving reference fields and one intentionally empty reference; an actual controlled Player-only mutation was correctly detected by the native comparer. Because strong scene references can themselves force assets into a game and conceal a missing-source issue, the next (schema-two) source adds a separate `Resources.Load` path-only mode. The default direct-source mode remains available but its possible build-inclusion side effect must be disclosed. The buyer-facing instructions now live in the shipped `Assets/HPRPlayerReferenceProbe/README.md`, correcting the original official Asset Store Tools documentation warning. The path-only revision requires a new separate first-party archive, new Editor/Player native receipts and official Asset Store Tools validation; do not reuse earlier proofs as if they covered these changes.
